API Reference

Every exported name, grouped the way a run uses them: grid and state, parameters and mask, the sheet options, the solvers, the simulation and its output. The Tutorial explains when to pick each option.

Backend selection

Shakti — Module

A Julia solver for the SHAKTI subglacial hydrology model (Sommers, Rajaram & Morlighem, 2018, https://gmd.copernicus.org/articles/11/2955/2018/): a continuum model of hydraulic head, effective pressure, water flux, and drainage-system geometry (gap height) beneath a glacier or ice sheet, that transitions smoothly between laminar (distributed) and turbulent (channelized) flow regimes rather than treating them as separate model components.

Built on Grid/State/Simulation (see their own docstrings): construct a Grid and State, populate the state with set_initial_conditions!, wrap everything in a Simulation (choosing a linear solver, sliding law, melt input, and observer), then call run!. Runs on CPU (Threads) or GPU (CUDA/Metal) backends, selected via Preferences-backed backend/floattype constants (see LocalPreferences.toml) rather than a runtime argument, so every kernel can be compiled once for the right array/element type.

Grid

Shakti.Grid — Type

A regular Cartesian grid of nx * ny cells with cell-center coordinate vectors x/y starting at the origin. lx/ly is the distance between the outermost cell centres (dx = lx/(nx-1)), so the cells themselves cover (lx+dx) * (ly+dy). dx2/dy2 are dx^2/dy^2, precomputed once since they appear in every finite-difference/finite-volume stencil in the solver.

source

State

Shakti.State — Type

Every field of the subglacial hydrology solve: cell-centered quantities (hydraulic head, water and overburden pressure, effective pressure, gap height, melt rate and its three heat-source components, ...) and the x-/y-face quantities needed for the finite-difference flux/gradient stencils (Nx+1 x Ny and Nx x Ny+1 respectively). Every field shares one array/element type A, so switching backend or floating-point precision (see the Preferences-backed backend/floattype constants in Shakti.jl) only ever touches Grid/State construction, not the kernels that operate on them. Build one with State(grid), then populate it via set_initial_conditions!.

Model parameters

Shakti.ModelParameters — Type

Physical constants and model parameters shared by every kernel, plus three precomputed "canonical" exponents (n_exp, n_minus_1_exp, inv_n_exp) used for fast exponentiation of Glen's-flow-law-style powers – see the module-level note below the constructor for why. Build one with the keyword constructor below rather than this positional one directly.

Mask

Shakti.GROUNDED — Constant

Mask value: dynamic hydrology solved here (Picard/Poisson elliptic solve + gap-height evolution).

source
Shakti.OCEAN — Constant

Mask value: Dirichlet boundary, pw = p_atm - rho_sw*g*min(zb, 0) (zb = bedrock elevation relative to sea level, positive up, so a marine bed at zb < 0 gets the correct hydrostatic pressure at depth -zb; rho_sw is seawater density, since this is the ocean's own hydrostatic pressure rather than the subglacial drainage system's).

source
Shakti.LAND — Constant

Mask value: Dirichlet boundary, pw = p_atm (0.0 by default).

source
Shakti.OTHER_BASIN — Constant

Mask value: not solved here; frozen row. Any GROUNDED neighbour treats the shared face as zero-flux (Neumann), and any face-based quantity (dhdx, dpwdx, q_x, ...) touching this cell is zeroed.

source
Shakti.compute_face_masks! — Function
compute_face_masks!(s::State) -> State
compute_face_masks!(s::State, land::Bool) -> State
compute_face_masks!(
    s::State,
    land::Bool,
    ocean::Bool
) -> State

Recomputes s.valid_x/s.valid_y from s.mask. Must be called (directly, or via set_initial_conditions!) any time s.mask changes.

Notes

A face is invalid iff either cell it connects is OTHER_BASIN or FROZEN_BED: that cell's hydrology isn't solved, so any gradient computed across that face would spuriously reflect a frozen, non-evolving neighbour value rather than a real head/pressure difference. LAND and OCEAN faces are left valid, since those are genuine (Dirichlet) drainage boundaries where a real flux is physically meaningful.

With land = true (ocean = true), a LAND (OCEAN) face is additionally closed where the boundary's fixed head lies above the neighbouring grounded cell's, so the boundary drains the ice but never feeds it (under SheetTopPotential, where the boundary head lies above the grounded cell's water level h + b, with the face's gap jump s.db_x/s.db_y). The arguments default to false here; the simulation passes ModelParameters' outflow_only_land/ outflow_only_ocean, both on by default (set outflow_only_ocean = false to let ocean water into the bed, e.g. tidal intrusion). The setup and mask helpers call it without them, and refresh_state! (run at construction and by the Simulation methods of the mask helpers) or the next step's refresh closes those faces.

The open/closed state is re-decided from the current head on every Picard iteration (see refresh_head_dependents!). On the 8-dataset check this cost up to ~2x wall time (Thwaites 2 km, pan-Antarctica 16 km). Deciding it once per time step instead was tested (branch outflow-faces-per-step) and is not the fix: it was slower still (pan-Antarctica 16 km 150 s vs 55 s, Helheim 500 m 23 s vs 9 s) and less robust (Helheim 500 m b_max 18.6 m vs 0.25 m), since faces lagged by a step let boundary water in. The extra cost is the harder problem with those faces closed.

source
Shakti.FROZEN_BED — Constant

Mask value: a genuinely frozen bed – no water, so no gap height (b=0) and no water pressure (pw=0, giving N=po exactly; see compute_N!). Otherwise handled identically to OTHER_BASIN: not solved here (frozen Dirichlet row in the elliptic solve), any GROUNDED neighbour treats the shared face as zero-flux, and any face-based quantity touching this cell is zeroed. Distinct from OTHER_BASIN (which is a domain-restriction category – real ice just outside the region being solved, pw held at whatever p_atm happens to be) precisely in that N is computed here rather than reported as 0, and its own pw is pinned to exactly 0 regardless of p_atm. Transition a cell to/from FROZEN_BED at runtime with freeze_cells!/thaw_cells! (frozen_bed.jl), or let update_frozen_mask! drive them from a basal-temperature field and the T_freeze/ T_hysteresis parameters.

Shakti.set_mask! — Function
set_mask!(
    s::State,
    p::ModelParameters,
    new_mask::AbstractMatrix
) -> NamedTuple{(:n_on, :n_off, :discarded_b, :n_isolated), <:NTuple{4, Any}}

Reclassifies cells to a host model's current mask new_mask (codes GROUNDED, OCEAN, LAND, OTHER_BASIN; e.g. where the ice-sheet model has grounded ice it solves), keeping FROZEN_BED cells frozen where the host still has them grounded (the frozen bed is handled by update_frozen_mask! after this). Call it at each coupling step, before the hydrology step, so Shakti never solves where the host has no grounded ice and never ignores where it does.

  • A cell that stops being GROUNDED loses its gap and water (discarded, returned as in update_frozen_mask!) and takes the prescribed pw of its new category (apply_boundary_pw!).
  • A cell that becomes GROUNDED is seeded at b = p.b_min with no water, as a thawing cell is; its pw (the Dirichlet value of its old category) is the initial guess of the next head solve.

Then refreshes the mask-dependent fields as freeze_cells! does. Returns (n_on, n_off, discarded_b, n_isolated).

source
Shakti.freeze_cells! — Function
freeze_cells!(
    s::State,
    p::ModelParameters,
    freeze_mask::AbstractMatrix{Bool}
) -> State

Freezes every cell where freeze_mask is true and currently GROUNDED to FROZEN_BED (cells freeze_mask marks that are already something else – OCEAN/ LAND/OTHER_BASIN/already FROZEN_BED – are left untouched, so passing an overly broad mask is harmless, not an error).

Sets b:=0 and pw:=0 on those cells, and zeroes the water W, then refreshes everything that depends on s.mask/s.b/ s.pw: s.h = zb on those cells (pw = 0; the other cells keep their head), the cell-centred s.K (b=0 gives K=0 exactly; the face transmissivities are rebuilt by the next refresh), s.valid_x/s.valid_y via compute_face_masks!, and s.N via compute_N! – which, per FROZEN_BED's own convention, evaluates to po - 0 = po exactly there: full overburden, no water pressure. s.dpwdx/s.dpwdy are left stale here deliberately – they're recomputed from the current h/pw at the top of every Picard iteration during the next step_h! anyway, so refreshing them now would just be redone.

For a threshold-based driver on a basal-temperature field, see update_frozen_mask!, which calls this (and thaw_cells!) for you. These State methods know none of the simulation's options (cell N clamps, outflow-only faces, face scheme); the Simulation methods, freeze_cells!(sim, freeze_mask) and likewise for thaw_cells!, set_mask! and update_frozen_mask!, refresh the derived fields with them afterwards (refresh_state!).

Limitation

Freezing is a cutoff, not a phase-change model: any water still held in a freezing cell (the filled gap and any uplift layer) is discarded, not refrozen onto the ice base, and no latent heat is applied. Gradual refreezing is the job of the energy balance already in compute_mdot! (the q_T conductive-loss term drives mdot < 0 and shrinks b on cold ice), so a more negative T_freeze lets that dry the cell out first and leaves less to discard. update_frozen_mask! reports the discarded amount so the size of this mass loss can be checked.

source
Shakti.thaw_cells! — Function
thaw_cells!(
    s::State,
    p::ModelParameters,
    thaw_mask::AbstractMatrix{Bool}
) -> State

Thaws every cell where thaw_mask is true and currently FROZEN_BED back to GROUNDED (same "only touches cells actually in the expected starting category" behavior as freeze_cells!).

Reseeds b:=p.b_min (a cell can't re-enter the dynamic assembly at literal b=0 – see FROZEN_BED's own docstring for why – compute_b!'s usual kernels take over evolving it normally from here on), with no water (W = 0): an empty cavity under UnfilledCavities, a dry floor under dry_floor. The Simulation method's refresh brings W within its sheet (constrain_water!), so only the filled sheet without the dry floor, whose water is b itself, starts these cells with b_min of water. pw/h are deliberately left untouched: a thawing cell starts from whatever it was while frozen (pw=0/dry/high-N if it was actually frozen via freeze_cells!) and the head equation evolves it from there on the next solve. Refreshes s.K/s.valid_x/s.valid_y/s.N the same way freeze_cells! does.

Shakti.update_frozen_mask! — Function
update_frozen_mask!(
    s::State,
    p::ModelParameters,
    T_prime_b::AbstractMatrix
) -> NamedTuple{(:n_frozen, :n_thawed, :discarded_b, :n_isolated), <:NTuple{4, Any}}

Updates s.mask between GROUNDED and FROZEN_BED from the basal temperature relative to pressure melting T_prime_b (K, an array the same shape as s.mask, e.g. Yelmo's T_prime_b), using p.T_freeze and p.T_hysteresis:

  • a GROUNDED cell with T_prime_b < T_freeze freezes (freeze_cells!);
  • a FROZEN_BED cell with T_prime_b >= T_freeze + T_hysteresis thaws (thaw_cells!);
  • anything else keeps its current state (this band is the hysteresis that prevents flicker).

Thawed cells restart at p.b_min (see thaw_cells!). With b_min = 0 that is b = 0, and a cell whose own b and all neighbours' b are zero has an all-zero matrix row – the same singular system a GROUNDED cell can reach on its own once b creeps to zero in a zero-b patch (CholeskyDirectSolver throws PosDefException; CUDSSDirectSolver does not check and silently returns garbage). A thawing block makes that certain for its interior, so use b_min > 0 (e.g. 1e-3) in runs that thaw regions.

Cells that are not GROUNDED/FROZEN_BED (OCEAN/LAND/OTHER_BASIN) are never touched. The refresh work in freeze_cells!/thaw_cells! only runs on calls where a transition actually happens. Intended to be called whenever the basal temperature is refreshed (thermodynamic timescale), not every hydrology step.

Returns (n_frozen, n_thawed, discarded_b, n_isolated): the number of cells that changed each way, the sum of the water depth (m; the water W, the filled gap plus the uplift layer) over the freezing cells, i.e. the water thickness discarded by freezing (multiply by dx*dy for a volume, see the limitation note in freeze_cells!).

source
Shakti.freeze_isolated! — Function
freeze_isolated!(s::State, p::ModelParameters) -> Any

Freezes (freeze_cells!) every GROUNDED cell none of whose four neighbours is GROUNDED, LAND or OCEAN: all its faces are closed (frozen, OTHER_BASIN or the domain edge), so its water has nowhere to go and, where its creep term vanishes (e.g. N = 0 under N_min = 0), its head-equation row is all zero and the solve fails. Freezing such a cell can isolate no other one (an isolated cell has no GROUNDED neighbour), so one pass suffices. One stencil kernel and a count, run where the mask changes, not per step. Returns the number of cells frozen.

Shakti.freeze_on_capacity! — Function
freeze_on_capacity!(
    C,
    sim::Simulation;
    dt,
    water_limited
) -> Any

Freeze-on capacity [m/s of ice] of every GROUNDED cell for a host's capacity basal boundary condition, from the current state (call it before the host's thermodynamic step, i.e. with this step's b and the last step's N and |u_b|): the fastest freezing the next gap update can absorb without b falling below p.b_min, see freeze_on_capacity_cell. Zero off GROUNDED. Under UnfilledCavities (water_limited = true, the default; false restores the gap-room limit alone) the capacity is also capped by the water actually present, (rho_w/rho_i)*W/dt (s.W): freezing consumes water, which an empty cavity does not have. Without the cap a dry cell can freeze water that is not there (about 3 times the melt supply on Greenland 16 km). Freezing closes the gap by the ice thickness and expels the excess water into the flow, so the limit is gap room, not water mass, and the result is local (no inflow term). Under the dry floor (dry_floor) the water W replaces b - b_min as the room, and the capacity is capped by the water too, (rho_w/rho_i)*W/dt (freeze_on_capacity_dry_floor_kernel!): a gap the update may drain to zero can freeze only the water it holds.

Where each term is evaluated follows the gap scheme in use: FullyImplicitGapScheme takes opening by sliding and creep at b_min, ImplicitGapScheme sliding at the old b (lagged beta) and creep at b_min, ExplicitGapScheme both at the old b. Under WithDiffusion it follows SUHMO's local terms (freeze_on_capacity_cell_diffusion) and ignores the diffusion of b, which only moves gap volume between grounded cells: C is then conservative where b is a local minimum and generous where it is a local maximum.

dt [s] is the interval the host applies C over, used for the gap-room term (b - b_min)/dt; it defaults to Shakti's own step. When Shakti subcycles within a longer host step (e.g. Yelmo advancing in dt_min chunks while Shakti steps hours), pass the host's step: the room in the gap is a stock, available once per host step, so spreading it over Shakti's short step would overstate C by the ratio of the two steps. With such a longer dt, opening by sliding and creep are also evaluated at the current gap rather than at b_min: over many Shakti steps creep keeps closing the gap at its actual size, and evaluating it at b_min (right for one implicit step) overstated C.

Melt input

Shakti.AbstractMeltInput — Type

How s.ieb (englacial-to-bed meltwater input, e.g. moulins/crevasses) is set up and evolved over time – multiple dispatch on the concrete subtype picks a fixed field (ConstantMeltInput), a time-varying seasonal cycle (SeasonalMeltInput), or a spatially-localized, time-ramped point source (GaussianMoulinMeltInput). Every subtype implements update_ieb! (called once per real timestep, outside the Picard loop, so s.ieb stays fixed across every Picard iteration within that timestep).

s.ieb is the sum of two parts, formed by combine_ieb!: s.ieb_own, Shakti's own input (seeded by set_initial_conditions! and, for the time-varying subtypes, rewritten by update_ieb!), and s.ieb_external, water supplied by a coupled model (e.g. Yelmo's englacial drainage melt_int), set with set_ieb_external! and zero when Shakti runs standalone. s.ieb is read directly (ieb[i, j]) inside linear_solver.jl's @parallel assembly kernels – neither of those needs to dispatch on the concrete AbstractMeltInput subtype.

source
Shakti.ConstantMeltInput — Type

A time-independent own input: whatever was seeded into state.ieb_own during set_initial_conditions! is used unchanged for the whole run. update_ieb! only re-forms ieb = ieb_own + ieb_external, so a coupled model's ieb_external is picked up each step.

source
Shakti.SeasonalMeltInput — Type

Reproduces the seasonal-cycle experiment from the original SHAKTI paper (Sommers et al. 2018, Sect. 3.3): i_e->b is applied uniformly over the whole domain, held at a winter baseline (i_min) except during a cosine-shaped melt-season window [t_start, t_start+period] (year fraction), where it swings up to a summer peak and back down to i_min at both ends of the window.

Notes

Holds only scalar fields (no arrays): like ConstantMeltInput/Arithmetic/ Harmonic, this struct is passed by value into linear_solver.jl's @parallel kernels, which requires kernel arguments to be bitstypes – an array field would break that. omega (2*pi/period) is precomputed once at construction rather than recomputed every update_ieb! call, same idiom as model_parameters.jl's canonical_exponent.

source

update_ieb!(_::ConstantMeltInput, state::State, t) -> State

ieb_own never changes after set_initial_conditions! under ConstantMeltInput; only re-forms ieb = ieb_own + ieb_external (identical to ieb_own when ieb_external is zero).

source
update_ieb!(mi::SeasonalMeltInput, state::State, t) -> State

Updates state.ieb_own (uniformly over the whole domain) for the current simulation time t (elapsed seconds, see run.jl's total_time), following mi's cosine-shaped seasonal cycle.

Notes

Called once per real timestep, outside the Picard loop, so state.ieb stays fixed across every Picard iteration within that timestep – same as ConstantMeltInput's ieb being fixed for the whole run. The t input is elapsed simulation time in seconds.

source
update_ieb!(
    mi::GaussianMoulinMeltInput,
    state::State,
    t
) -> State

Updates state.ieb_own to mi.shape * Q_max * min(t/ramp_duration, 1) – the fixed spatial Gaussian footprint scaled by the current point on the linear ramp (elapsed simulation time t, seconds).

source
Shakti.GaussianMoulinMeltInput — Type

A single point source (moulin) with a fixed 2D Gaussian spatial footprint and a linear temporal ramp from 0 at t=0 up to its full discharge Q_max at t=ramp_duration, held constant thereafter – reproduces Felden et al. (2023, SUHMO)'s Sect. 4.2 channelized convergence test case ("the moulin source term follows a spatial Gaussian profile... the moulin input is gradually increased in time, from 0 at time t=0s to the maximum value after about a month"). The paper doesn't give the Gaussian's exact width or the ramp's exact functional shape – sigma and the choice of a plain linear ramp (vs. e.g. a smoothstep) are this port's own, reasonable but unverified-against-the-paper choices.

Notes

Unlike SeasonalMeltInput, this DOES hold a full (Nx, Ny) array field (shape) – fine here since mi itself is never passed into a @parallel kernel (only update_ieb!'s own plain broadcast reads it, same as how LinearSlidingLaw's C field holds a full array). shape is precomputed once at construction, normalized so sum(shape)*dx*dy ≈ 1 (an un-truncated Gaussian integrates to exactly 1 over the whole plane; on a finite domain this is only approximate, good enough as long as sigma is small relative to the domain size, as it is here).

K-face scheme

Shakti.AbstractKFaceScheme — Type

How hydraulic conductivity K is combined across two neighbouring GROUNDED cells' shared face into a single face conductance – multiple dispatch on the concrete subtype picks arithmetic or harmonic averaging, the donor cell's value (Upwind), or the donor's value at the end-of-step water depth (ImplicitUpwind) (see compute_K_face and boundary_K_face).

source
Shakti.Arithmetic — Type

Arithmetic-mean face conductance.

source
Shakti.Harmonic — Type

Harmonic-mean face conductance: penalizes a face where either neighbour has low conductivity more strongly than the arithmetic mean does.

source
Shakti.Upwind — Type

Upwind (donor-cell) face conductance: the value of the cell the water flows OUT of, i.e. of the higher-head cell (the smaller one when the head difference is zero). A cell that is nearly empty then cannot discharge through the (much larger) conductance of the cell it flows into, which an average would allow: outflow is limited by the water depth of the donor, as for free-surface flow. Needs the head difference across the face, dh = h[i] - h[i-1]; the K-face schemes that do not use it ignore it. Evaluated from the previous Picard iterate's head (like every other coefficient); a face coefficient is still one number per face, so the assembled matrix stays symmetric.

source
Shakti.ImplicitUpwind — Type

Upwind face conductance built from the donor's water depth at the END of the step, as a function of the head iterate, instead of at its start: W = b - max(0, zb - h) in a cell whose gap may be partly empty (UnfilledCavities) and W = b + max(0, h - h_o) in one where the ice may be lifted (IceUplift), b itself held at its start-of-step value as everywhere else (compute_b_w_iterate!, unfilled_cavities.jl). Where the water depth is free (a free surface or an uplift layer) the flux is a kinematic wave in it, q ~ K(W) grad(zb): with W lagged (Upwind) that wave is explicit in time and stable only for dt < dx*W/(3|q|), minutes at 100 m. Here it is backward Euler and stable at any dt. Each head solve also takes the Newton terms of the face flux's dependence on the donor's water depth (water_depth_newton_kernel!, water_flux.jl), so the Picard iteration is Newton's method in W and converges at any dt (a plain fixed point in W does not, see compute_b_w!). Those terms couple each face to its donor cell only, so the assembled matrix is no longer symmetric: it needs LUDirectSolver or CUDSSDirectSolver(grid) (structure = :general, the default). Without unfilled cavities and uplift every water depth is the gap and this is Upwind exactly.

source
Shakti.compute_K_face — Function
compute_K_face(
    kfs::AbstractKFaceScheme,
    K,
    i1,
    j1,
    i2,
    j2
) -> Any

Face conductance between cells (i1,j1) and (i2,j2) from face_mean: (K[i1,j1] + K[i2,j2]) / 2 under Arithmetic, 2*K[i1,j1]*K[i2,j2] / (K[i1,j1] + K[i2,j2] + eps) under Harmonic, and the smaller of the two under Upwind when no head difference is given (the donor's otherwise, see the four-argument face_mean). ImplicitUpwind builds its faces in compute_face_flux! from the donor's water depth instead. Here @inline can help the compiler optimize its code and reduce the cost of function calls.

source
Shakti.face_conductance — Function
face_conductance(
    kfs::AbstractKFaceScheme,
    Ka,
    ma,
    Kb,
    mb
) -> Any
face_conductance(
    kfs::AbstractKFaceScheme,
    Ka,
    ma,
    Kb,
    mb,
    dh
) -> Any

Face value of a cell-centred conductance (Ka in a cell with mask ma, Kb in its neighbour with mask mb), symmetric in its two cells so both sides of a face read the same value – the face conductance compute_face_flux! (water_flux.jl) builds s.K_x/s.K_y from, and therefore exactly what the linear system assembles:

  • both GROUNDED: the K-face scheme's mean (kfs);
  • one GROUNDED, the other OCEAN/LAND: the grounded cell's own value (see boundary_K_face for why the Dirichlet cell's placeholder 0 must not be averaged in);
  • anything else (a face touching OTHER_BASIN/FROZEN_BED, or between two non-solved cells): 0, a zero-flux face.

Unfilled cavities, water-surface potential, ice uplift (GlaDS-2 sheet)

Shakti.AbstractCavityFilling — Type

Whether the gap may be partly empty of water – multiple dispatch on the concrete subtype (FilledCavities/UnfilledCavities), chosen once by the caller of Simulation (keyword cavity_filling) – same "dispatch on a type decided once outside the hot loop" idiom as MeltTerms (melt_rate.jl) and AbstractOpenBySlidingScheme (gap_height.jl).

source
Shakti.FilledCavities — Type

SHAKTI's original sheet: the gap is always completely full of water, State.W = b (less the dry floor, dry_floor).

source
Shakti.UnfilledCavities — Type

The gap may be partly empty (free-surface regime, p_w = 0), see this file's header. A GROUNDED cell whose head falls below the bed takes the unfilled head row (cavity_head_terms, linear_solver.jl): N = po, and the empty depth zb - h is the cell's storage. Shakti.compute_b_w! — Function
compute_b_w!(s::State, p::ModelParameters) -> State

Water depth s.b_w = W as the step starts (s.W, the water present: the gap less its empty part under UnfilledCavities or the dry volume the b_min clamp keeps under the filled dry floor, plus the lifted layer under IceUplift), never below 0; exactly b under SHAKTI's original sheet. The face conductances (compute_face_flux!) are built from it, so an empty cavity neither carries nor draws water. No floor at min(b, p.b_min): a dry cell (W = 0) that kept that conductance drained water it did not have wherever its head stayed above a neighbour's (a margin cell on a slope next to LAND), and update_water_budget!'s floor W >= 0 then created it: 1.4 m^3/s on Drang Drung at 25 m, 21 times the melt input. Without the floor a dry cell's outflow vanishes with its water; its row stays regular through the unfilled storage 1/dt (cavity_head_terms), or is a closed cell's once all its faces carry no water. It is the water present at the start of the step, not at the current head iterate: like b in the legacy equations it stays fixed during the Picard loop. That lag makes the water-depth dependence of the flux explicit in time where the water depth is free (an unfilled or uplifted cell): a step longer than the time such a cell takes to fill or drain, about dx*W/(3|q|) (minutes at 100 m for a thin free-surface layer), overshoots, and the solution oscillates from step to step or Picard cycles. Taking the depth at the head iterate in a plain Picard iteration does not help: the one-cell Picard map then has slope ~ -3(W + dzb)/W, and neither Anderson acceleration nor a Jacobian-free Newton-Krylov solver (since removed) converged on the SHW12 benchmark at dt = 6 h. What does is the end-of-step depth together with the Newton terms of its dependence on the head, ImplicitUpwind (compute_b_w_iterate!). p is not used (kept for the call signature).

Shakti.compute_b_w_iterate! — Function
compute_b_w_iterate!(s::State, p::ModelParameters) -> State

    p::ModelParameters,

Water depth at the end of the step as a function of the current head iterate, for ImplicitUpwind, and its slope s.dbw_dh = dW/dh. With the gap G the head rows assume for the end of the step (gc): W = G(p_o) - (zb - h) where the gap may be partly empty (s.stor > 0, UnfilledCavities) and h < zb, W = G(0) + (h - h_o) where the ice may be lifted (s.stor_up > 0, IceUplift) and h > h_o, W = G(N) otherwise, never below 0 (no floor, see compute_b_w!). source
Shakti.ExplicitGapCoupling — Type

The original equations (the default before ConsistentGapCoupling became it wherever available, see Simulation): the head rows assume db = dt*rate(N, b_old), the gap rate at the new effective pressure and the old gap, with its creep term Newton-linearised in the head (gap_budget_terms). That is the explicit gap update; the implicit and fully implicit gap schemes move the gap by less when creep is fast, dt*A*|N|^(n-1)*N > 1, so the head equation and the gap disagree on the water stored: water is created or lost (under UnfilledCavities the difference stays in the water W, and the floor W >= 0 creates water), and the explicit closure in the head row overshoots (the gap would close by more than its height). At N < 0 (water above the overburden) creep opens the gap, which these schemes grow as exp(dt*|C|) while the head rows assume linear growth, so N does not recover; with b_max = Inf the gap can run away (check_gap_height reports it).

source
Shakti.ConsistentGapCoupling — Type

The head rows assume the gap change the gap scheme itself will make: db = G(N) - b_old, with G the update of the scheme in use (explicit, implicit or fully implicit, with the creep-length scheme and the b_min/b_max clamp), Newton- linearised in the head through N (dG/dh = -rho_w g dG/dN, by a central difference). The head equation and the gap update then store the same water at any dt (mass is conserved, the empty-volume bookkeeping of UnfilledCavities stays consistent with the head), and an implicit or fully implicit gap scheme stays implicit in the head equation too. With the explicit gap scheme it differs from ExplicitGapCoupling only by the clamp. Under WithDiffusion the gap update is SUHMO's coupled linear system: the head rows then take the gap that system gives at each head iterate (DiffusiveGapUpdate). The default wherever available (see Simulation). At N < 0 the head rows see the gap's exponential opening, so N recovers where the explicit coupling runs away; at large enough dt the Picard iteration itself stops converging and the gap can still run away (Helheim at 500 m, filled cavities: 5-day steps hold, 10-day steps do not), which check_gap_height reports.

Shakti.LUDirectSolver — Type

Direct solve via sparse LU factorization (SparseArrays/UMFPACK) of the assembled SparseAssembledLinearSystem: the CholeskyDirectSolver counterpart for a matrix that is not symmetric, which the head rows assemble under ImplicitUpwind (the Newton terms of the face fluxes' dependence on their donor's water depth couple each face to one side only). Refactorizes in place each solve, reusing the symbolic analysis since the sparsity pattern never changes. CPU-only, like CholeskyDirectSolver; about twice its cost per solve on the same matrix.

With lagged = true it does not refactorize every solve: it solves with GMRES (Krylov.jl), preconditioned by the last factorization it made, and refactorizes only when GMRES has not reached rtol within itmax iterations. Between Picard iterations, and between quiet time steps, the matrix changes little, so the old factors are a near-exact preconditioner and GMRES converges in a few iterations, each a triangular solve and a matrix-vector product, at well under the cost of the numeric factorization. At a regime change GMRES stalls, the solver refactorizes, and that solve costs itmax wasted iterations more than a direct one. The result agrees with the direct solve to about rtol relative to the right-hand side, not bit for bit.

Shakti.ChebyshevPreconditioner — Type

A GPU-capable, dot-product-free accelerated preconditioner for CGIterativeSolver: approximates A^-1 by a degree-degree Chebyshev polynomial in the Jacobi-scaled operator (Saad Algorithm 12.1), applied via LinearAlgebra.ldiv! below using only matvecs and axpy-style updates – no reductions (and so no GPU->CPU syncs) within one preconditioner application. lambda_min/lambda_max (the polynomial's eigenvalue bounds) are refreshed once per solve by update_chebyshev_bounds!, not on every ldiv! call.

Notes

Confirmed on real GPU hardware (see the module-level note above) that this does NOT eliminate CG's own per-iteration host syncs (those come from CG's own dot products, not the preconditioner) – measured to lose to plain Jacobi in wall time at the grid sizes tested. Kept available as an option (and the only GPU-capable accelerated one) since a differently-shaped or larger problem could tip that balance; AMGPreconditioner is the better choice when available (CPU/SparseMatrixCSC-only).

Shakti.AndersonHeadRelaxation — Type

Anderson acceleration (depth depth, mixing/damping beta) of the Picard fixed-point map h -> solve_elliptic_linear_system!(...). Instead of blending the new head with just the immediately preceding iterate (as UnderHeadRelaxation does, with a fixed weight), Anderson acceleration keeps the last depth (iterate, residual) pairs and, each iteration, solves a small (at most depthxdepth) least-squares problem for the linear combination of past residuals that comes closest to canceling the current one, then extrapolates the next iterate using those same weights. This is the standard "Type-I" formulation (residual-difference least squares – Walker & Ni, SIAM J. Numer. Anal. 49(4), 1715-1735, 2011; Fang & Saad, Numer. Linear Algebra Appl. 16(3), 2009), reformulated in terms of increments (ΔX/ΔF) rather than the equivalent constrained-weights form, since increments avoid needing to explicitly enforce sum(alpha) = 1.

beta = 1 recovers "pure" Anderson extrapolation (no extra damping beyond what the least-squares step itself provides); beta < 1 mixes in some of UnderHeadRelaxation's damping on top, which may help stability on stiff problems at the cost of some acceleration.

Solves the least-squares problem via Julia's `on the talln x mkmatrixΔFdirectly (a Householder-QR-based solve, dispatched automatically for a non-square left-hand side), NOT the earlier normal-equations formulation ((ΔF'ΔF) \ (ΔF'fk)) -- normal equations squareΔF's condition number, a real risk once consecutive residual differences become nearly collinear (typically once the residual is already small), and were the most likely explanation for a specific failure mode measured empirically: on the *synthetic* benchmark (beyondsolverchoice.tex), depth 5-8 sometimes extrapolated in the wrong direction, needing *more* total iterations than plain Picard, non-monotonically in depth.gammaclipremains as a cheap safety net even with the more robust QR solve (a genuinely rank-deficient/near-collinearΔFcan still produce huge weights): whenever the solved weights blow up (maximum(abs, gamma) > gamma_clip), the extrapolation is discarded and this one iteration falls back to a plain beta-damped step instead of applying a wild, unreliable correction toh`.

Real-dataset caveat (important – read before using this on anything beyond a quick experiment): on the real Drang Drung v2 dataset (test/drangdrung/drangdrung_anderson_compare.jl), depth 3 (the setting that looked best on the synthetic benchmark) was a clear, consistent net loss at every one of 30 real timesteps tested – 46% more Picard iterations and ~2x more wall time than plain Picard, not an occasional fluke. The synthetic benchmark's spatially-uniform coefficients (flat slope, constant viscosity/friction) apparently make it an easier fixed-point map to extrapolate than a real, spatially-heterogeneous problem (real ice thickness/friction/mesh geometry) is. Do not assume the synthetic-benchmark depth=3 result transfers to a real simulation without checking on that specific dataset first – this relaxation scheme is currently NOT recommended for production use on real data, opt-in-only, kept for further experimentation (e.g. once a scenario is found where it does help, or if this QR-based solve changes the picture where the normal-equations version didn't – re-validate this claim itself when testing that).

History is reset once per Picard loop (see reset_relaxation!/Picard_loop!): different timesteps solve a different fixed-point map (the Newton-linearization point and boundary data both change), so carrying history across timesteps would extrapolate against a stale map.

Implicit (backward-Euler) update of b: the creep-closure term is unconditionally stable at any dt, but the opening-by-sliding term (beta(b)*|u_b|, active when p.br != 0) is still evaluated at the lagged b (last step's value, via s.beta) rather than the new one – so this scheme inherits a real, if usually generous, dt cap from that term whenever p.br != 0 and b < p.br (beta = (br - b)/lr, so the explicit opening overshoots br once dt*|u_b|/lr > 1). Confirmed in practice, not just in theory: a real AIS 32km run hit this at dt=900s and blew b up to the b_max safety cap in one cell, something FullyImplicitGapScheme – now the default – doesn't do. Unconditionally stable outright when p.br == 0. Deprecated: FullyImplicitGapScheme has the same cost without that cap; selecting it warns, and the scheme will be removed.

source
Shakti.FullyImplicitGapScheme — Type

Fully implicit update of b: both the creep-closure term AND the opening-by-sliding term are evaluated at the new (k+1) b, not the lagged one – unconditionally stable for any dt, regardless of p.br. beta(b) = max(0, (p.br-b)/p.lr) is piecewise-linear (not smooth, but not genuinely nonlinear either), so this doesn't need a Newton iteration: compute_b_fully_implicit_kernel! solves both linear branches (b_{k+1} < p.br and b_{k+1} >= p.br) in closed form and picks whichever is self-consistent with its own assumption. Same per-step cost as ImplicitGapScheme (often cheaper in practice, since Picard convergence tends to benefit from not carrying the spurious runaway/clamp events ImplicitGapScheme is prone to) – no extra iteration. The default choice – confirmed against ImplicitGapScheme and ExplicitGapScheme in a 6-dt/2-domain (AIS/GrIS) sweep: all three agree closely at the finest dt (<0.3% relative RMSE), and FullyImplicitGapScheme tracks ImplicitGapScheme far more tightly than ExplicitGapScheme does as dt grows coarser.

Initial guess for each timestep's head solve, extrapolated in time from the last converged heads (held by Simulation as he, applied by step! before the head solve). Multiple dispatch picks NoHeadExtrapolation (start from the previous step's head, the original behaviour) or HeadExtrapolation.

Shakti.NoHeadExtrapolation — Type

source
Shakti.HeadExtrapolation — Type

Polynomial extrapolation in time of the head, of degree order (1 = linear, 2 = quadratic, ...), through the last order + 1 converged heads, evaluated at the new step's end time – a better starting point for the Picard/Newton iteration than the previous head alone, which needs fewer iterations to reach the same tolerance (the answer itself is unchanged: only the starting point moves).

Notes

  • Only converged heads enter the history. The initial condition is not a solution of the head equation, so the first extrapolation happens at the third step (linear) – until enough history exists, the highest degree the available heads allow is used, down to none. A step that fails to converge clears the history, so a bad head is never extrapolated from.
  • Weights are Lagrange weights on the actual step end times, so variable dt (AdaptiveTimeStep) is handled exactly.
  • Only GROUNDED cells are extrapolated: Dirichlet (OCEAN/LAND) heads are fixed, and OTHER_BASIN/FROZEN_BED rows hold their current value, which extrapolation would make drift.
  • Memory: order + 1 head-sized arrays. Cost per step: order + 1 fused broadcasts.
  • The englacial storage (p.e_v > 0) and the water test take the head at the start of the step, which prepare_head_solve! keeps in the solver's h_old before the guess replaces s.h.

source
Shakti.AdaptiveTimeStep — Type

Chooses sim.dt[] every step by how the head solve converges, between dt_min and dt_max, and stops run! at target_time. Under the default sheet the gap update is fully implicit and unconditionally stable, so what limits the step is the Picard iteration at regime changes (cells filling, emptying or lifting the ice), not a relaxation rate of the gap:

  • a step whose head solve does not converge is rejected: the head is reset to the start of the step and the step is retried at half the dt, down to dt_min (a step at dt_min is kept whether it converged or not);
  • after grow_after steps in a row that converged within fast_iters iterations, dt grows by the factor grow.

The step that dt starts from is the Simulation's own dt. Only the head solve is redone: the gap, the water W, the start-of-step melt and the head history change only once a step is accepted.

Optionally dt is also capped by the local relaxation rate of the gap equation, C + gamma = A_visc*|N|^(n-1)*N + |u_b|/lr (compute_dt_rate_kernel!), over the cells whose gap is above b_min (a gap at b_min is held there: creep closes it within minutes under thick ice and nothing changes): dt <= safety_factor / stat, where stat is the maximum of that rate (UsePercentile=false, a single GPU-native reduction) or a chosen percentile of it (UsePercentile=true, a sort and a host transfer each step, less swayed by one outlier cell). This is an accuracy cap only; it is off unless safety_factor is given. UsePercentile is a type parameter, so the choice is two rate_statistic methods rather than a branch in the per-step reduction. The rate is taken from the previous step's converged N/u_b, the same lagged-coefficient idiom as s.beta in ImplicitGapScheme.

Build with the AdaptiveTimeStep convenience constructor below, not this one directly – it sizes rate_field/host_rate/scratch correctly.

Shakti.CreepCutoff — Type

Felden et al. (2023, SUHMO, https://doi.org/10.5194/gmd-16-407-2023) Eq. 7's creep length scale: l_c = b*(1 - (b_c-b)/b_c) = b^2/b_c for b <= p.b_c, else l_c = b (continuous at b = p.b_c). Below the cutoff, ice-creep closure (A|N|^(n-1)*N*l_c) scales as b^2 instead of b, cutting it off faster than the standard linear term as b -> 0 – intended to let sheet-like drainage survive in places where the linear closure would otherwise close it out entirely. Selected automatically when p.b_c != 0.

Known instability – NOT safe to enable without checking for near-flotation cells first

Real-dataset testing (2026-09-16, real-dataset SUHMO test pass; reconfirmed 2026-09-17 against this exact code via a shortened reproduction, both in project memory/suhmo.tex) found CreepCutoff triggers an unbounded gap-height runaway at cells where N goes deeply negative while b is still below b_c. On Helheim (b_c=0.05, b_max=Inf), one cell reached b=70.66m/K=8.1e10 by the end of a 90-day run (baseline: b=0.27m) – and the 2026-09-17 check reproduced the same divergence at the same cell (b~3.9m by day 30) from a fresh run, confirming this is not an artifact of one earlier run.

Mechanism (implicit_creep_update, this file): while b <= b_c and N < 0 (so the closure coefficient C = A|N|^(n-1)*N is negative), the cutoff branch used to return b_below = b_old + dt*opening directly, dropping the (1 + dt*C) implicit-closure term in that regime, unlike StandardCreep. b then grew by the bare opening term every step until it crossed b_c onto the linear branch, by which point the growth did not turn over. That branch now falls back to the StandardCreep form at C <= 0 (relax_update: the exact exponential at N < 0); the real-data runs above predate that change and have not been repeated, so the caution below stands.

Not a generic problem: clean (1 Picard iteration/step, no instability) on 3 of 5 real datasets tested (Drang Drung, Thwaites, Pan-Antarctica) at the same or larger b_c. Failed only on the two datasets with known persistent near-flotation cells – Helheim (uncontained runaway) and Greenland (contained non-convergence, ~1% of steps, no NaN/Inf). The datasets that stayed clean already use CellNClamping at their own known-unstable cells (Thwaites, Pan-Antarctica), for reasons predating this branch – Helheim does not, and has no finite p.b_max either.

Before enabling CreepCutoff (p.b_c != 0) on a new dataset: check for cells with a persistent or deep negative-N excursion and consider CellNClamping there, and set a finite p.b_max. Neither is a confirmed complete fix – Greenland had CellNClamping and still saw contained non-convergence – so treat this as a real, open risk to check for per-dataset, not a solved problem. See test/helheim/diagnose_creepcutoff_runaway.jl for the original root-cause trace.

Whether b's evolution includes the new channel-wall diffusion term (∇·(D∇b), Felden et al. 2023 – SUHMO – Eqs. 9-11, https://doi.org/10.5194/gmd-16-407-2023) – multiple dispatch on the concrete subtype (NoDiffusion/WithDiffusion) picks whether the diffusion coefficient D (s.D_x/s.D_y, melt_rate.jl's compute_D!) is refreshed every Picard iteration and whether b's own timestep update solves the coupled diffusion system at all, same "dispatch on a type decided once outside the hot loop" idiom as AbstractOpenBySlidingScheme/ AbstractCreepLengthScheme (gap_height.jl). Defined here (not in gap_height.jl, where those two live) because WithDiffusion bundles its own AbstractLinearSolver – b's own diffusion operator needs a second, independent linear solve alongside h's (different sparsity coefficients: 1 plus face diffusivities vs. h's Newton-linearized creep-closure reaction term), not a shared one – and this file (linear_solver.jl) is included well before elliptic_solver.jl, whose refresh_head_dependents!/Picard_iteration! need AbstractDiffusionScheme in scope to type-annotate ds.

Running a simulation

Shakti.run! — Function
run!(
    sim::Simulation;
    checkpoint_every,
    checkpoint_path,
    restart_path,
    extend_path
)

Runs sim from t=0 (or from a checkpoint, see restart_path/extend_path) up to sim.tsteps, calling step! each iteration and recording output via sim.observer.

Notes

checkpoint_every/checkpoint_path: if both given, sim.state is saved to checkpoint_path (overwriting the previous checkpoint – only the latest is kept) every checkpoint_every tsteps, so a run killed at any point can be resumed via restart_path below instead of starting over from t=0. The loop's actual last step is also always checkpointed on top of that periodic schedule (whether or not it happens to be a checkpoint_every multiple), so a run that finishes cleanly never leaves its newest checkpoint stale. The same checkpoint also feeds extend_path, for the different "run finished, now go further" case – see that keyword's own paragraph for how the two differ.

restart_path: if given, resumes from a checkpoint written by a previous run! call instead of starting fresh at t=0 – loads sim.state/sim.total_time and continues the loop from the checkpointed tstep + 1 up to sim.tsteps (still the original total step count, not "how many more steps to do"). The observer's output file is reopened (not truncated) via resume! so it's appended to across the restart; see observer.jl for how each file writer handles a tstep that the crashed run may have already written. Use this when a run was killed partway to its original target and you want to finish reaching that same target in the same output file.

extend_path: the other way to start from a checkpoint, for the different case of a run that completed its original target and you now want to push it further (a new, larger sim.tsteps than the run that wrote the checkpoint had). Loads sim.state/sim.total_time/sim.dt from the checkpoint via the same load_checkpoint! restart_path uses, but then starts a fresh tracked-output file (via prepare!/observe!, the same path a cold start takes) instead of reopening the old one – the old file's own preallocated frame count was sized for its original, now-too-small target, and reopening a different path (the natural result of sim.tsteps changing, if your own script's output filename encodes it, as e.g. pan_antarctica_simulation.jl's does) would fail outright since that path doesn't exist yet. The loop itself then runs fresh from t=1 to sim.tsteps, so sim.tsteps here means "how many more steps to run," not the original run's total – unlike restart_path. The new file's frame 0 is stamped with the loaded total_time (not 0), so day-labels stay physically correct (e.g. day 200 -> 300, not 0 -> 100) even though it's a separate file from the original run's own output; a reader that wants one continuous timeseries needs to know to read both files in sequence. Mutually exclusive with restart_path – pass at most one.

Under AdaptiveTimeStep, the loop can also end before sim.tsteps if total_time[] reaches sim.ts.target_time first (the intended way to stop a time-targeted adaptive run, since the true step count needed to cover target_time isn't known in advance) – sim.tsteps itself should still be sized generously from AdaptiveTimeStep's own dt_min (see its docstring) so the loop is a real, finite upper bound either way, not just a number that happens to be big enough.
